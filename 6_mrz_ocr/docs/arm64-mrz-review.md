# ARM64 照片 -> MRZ 实现评审

评审对象：本仓库 `6_mrz_ocr` + `8_android` 已落地的 ARM64 (arm64-v8a)
MRZ 链路，基准是对一份通用《护照 OCR 移植到 Android ARM64》方案综述的
逐条核对。所有数字都来自本机的实测（C 侧合成基准、41 张真实照片端到端
评测、设备 192.168.26.181 上的 62 张批跑）。

## 0. 结论

现有实现已经**达到了综述里"方案 1：极致轻量专用 MRZ"的目标，并且比该方案
的指标更好**，同时也暴露了三处与综述差距明显的工程缺口。

| 维度 | 综述目标 | 本仓库实测 |
|------|----------|-----------|
| 模型体积 | < 3 MB | **40 KB**（两行模型各 10320 float） |
| 单次识别耗时 | < 15 ms | **native OCR 约 40 ms / 两行，decode 1.5 ms** |
| 端到端（照片 -> MRZ） | 未给 | **p50 56 ms，max 111 ms，62 张无一超 200 ms** |
| 端到端准确率 | 未给 | 41 张真图 **40/41**，假接受 0 |
| 推理引擎 | NCNN / MNN / ORT | **纯 C，无框架依赖**，`libmrz_jni.so` 1.2 MB |
| 字典 | 37 字符 | 37 字符，一致 |

综述是"选型指南"，本仓库是"已实现并实测"。两者的差别在于：综述推荐
YOLOv8n-pose + CRNN 的两段式检测识别，本仓库用的是**单段式**：行投影定位
两行 -> 直接切字 -> 逐字定长分类 -> ICAO checksum 约束搜索。把检测交给
IC 约束，反而绕开了综述方案里最难的一环（浅色防伪底纹下的文本行检测）。

## 1. 综述里已经被本仓库做掉的部分

### 1.1 业务场景切分（MRZ vs VIZ）

综述的核心判断是"只要 MRZ 就够，VIZ 需要另部署 10-25 MB 的通用 OCR"。
本仓库的选择与之一致：`PhotoMrzPipeline` 只做 MRZ，`PHOTO_METHODS` 里的
`paddle` / `mlkit` / `tesseract` 是对比用的实验通道，不在产品路径上。
**建议维持**：KYC 开户场景用 MRZ 已覆盖 95% 诉求；真要中文姓名/签发地，
应该单独排期一条 VIZ 通道，而不是把它塞进 200 ms 的实时链路。

### 1.2 44-Slot 定长分类头（综述称为"创新分支"）

综述建议"卷积下采样至刚好 44 个 Feature Token，直接接 44 个 37 维
Softmax 头，无需 CTC"。

本仓库的实现在**结构上等价但走的是另一条路**：`cnn.c` 不做序列建模，
每个字形独立走 `12x16 -> conv3 -> 96 维特征 -> FC -> 37 维 softmax`，
然后由 C 侧按列号拼成 44 位（`cnn_row_features_batch` / `cnn_fc_batch`）。
也就是说**没有 CTC，也没有 CTC 的对齐问题**，而且省掉了序列模型的延迟。
这是本实现在 ARM64 上只有 ~40 ms 的主要原因。

**代价**：切字必须准。切字错了，44-slot 结构无从补救。所以下面的
"切字鲁棒性"才是真正的瓶颈。

### 1.3 ICAO 9303 校验纠错

综述说"当且仅当某一位校验失败时，可调取 Softmax 的 Top-2 候选值，结合
校验和公式执行约束求解"。

本仓库实现得更彻底：`mrz_beam_search()` 是一个**带可采纳上界剪枝的深度
优先搜索**，在 14 个最不确定的列上最多改 4 个字符，每个叶子都过 5 个校验
位打分。关键在于**搜索在 checksum 通过时也会运行**——因为"校验通过"并不
等于"读对了"，一个把 B 读成 8 的结果照样可能让校验位成立。

实测收益（41 张真图，同权重同输入的 A/B）：

| | line2 in truth set | TRUE | FALSE |
|---|---|---|---|
| 旧（1-2 位置翻转，仅失败时搜） | 37/41 | 37/41 | 2 |
| 新（深 beam，始终运行） | **40/41** | **40/41** | **0** |

1380 张合成基准上 checksum-valid 率 **72.68% -> 96.09%**，full match
59.57% -> 64.42%。详见 `docs/deep-beam.md`。

### 1.4 轻量化与体积

- 模型 40 KB，`.so` 1.2 MB，**没有 ONNX Runtime / NCNN / MNN 依赖**；
- `cnn_fc_batch` 是手写 4-way unrolled 的标量 GEMM，循环顺序经过调整使
  权重行驻留 L1（`fc1_w` 24 KB + `fc2_w` 9 KB 原先按 glyph 外层循环会反复
  冲刷 L1），且**累加顺序未变，浮点结果逐位一致**（1380 张基准 byte-exact
  验证过）；
- 综述推荐的"FP16 打包 + INT8 量化"对本仓库**不适用**：模型只有 40 KB，
  量化收益可以忽略，而 FP16 会破坏已经 bit-exact 的回归基线。

### 1.5 端侧耗时控制

综述给的"方案 1：10-25 ms 实时 30fps"是**只算模型推理**。本仓库的口径是
**端到端**（含解码、行定位、切字、校验、纠错、跨线程回传），实测：

- 设备 `192.168.26.181`，62 张照片，产品默认路径；
- p50 56 ms / p95 88 ms / max 111 ms，**0 张超过 200 ms**；
- native 侧 decode（含深 beam）1.5 ms，OCR 两行约 40 ms，结构定位 3-6 ms。

工程上真正起作用的是三个东西，综述里没有提：

1. **行投影搬到 native**（`MrzNative.rowProfile`）。Kotlin 里做同样的
   luma 运算是 25-38 ms，native 之后 3-6 ms；
2. **两行并行**（`MrzNative.setParallel(true)`），双线 pthread 同时前向；
3. **兜底引擎的预算门控**（`FALLBACK_MIN_BUDGET_MS = 70`）。第二个引擎
   只在剩余预算 >= 70 ms 时才跑——超预算交付一个更差的结果不如干净地
   返回失败。

**一个已知的坏味道**：曾试图把像素读取改成分条带 JNI 调用，结果
`structure` 从 24 ms 涨到 130 ms（41 次 JNI 往返丢掉了缓存局部性），已
回滚。`GetPrimitiveArrayCritical` 区间内调用任何其它 JNI 函数会让 ART
直接 abort，必须先 `NewIntArray` -> critical 区内只读、写 C 容器 -> 退出
critical 区 -> `SetIntArrayRegion`。

## 2. 与综述差距明显、需要决策的地方

### 2.1 没有 NEON/SIMD（最大的工程缺口）

综述把"ARM NEON 汇编级优化"列为 NCNN/MNN 的首要优势。本仓库的
`cnn_fc_batch` 是**纯标量** 4-way unroll，编译器在 `-O2` 下能自动向量化的
空间有限（`CNN_FLAT=96`、`CNN_HIDDEN=64` 都不是 4 的整数倍对齐友好值）。

影响：native OCR 约 40 ms 是当前耗时的大头。**收益上限估计**：
fc1 是 96x64 = 6144 MAC/字，fc2 是 64x37 = 2368 MAC/字，44 字共约
37 万 MAC，NEON 4 路 SIMD 理论上能省 2-3 倍，即 native OCR 从 40 ms 降到
15-20 ms。

**建议**：先做 profiling 再决定。`MrzNative.setProfiling(true)` 已经能出
native 侧耗时，拆分 conv / fc / decode 三段占比后再动。

### 2.2 编译选项

综述建议：

```cmake
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -O3 -flto -fomit-frame-pointer")
add_definitions(-D__ARM_NEON -D__ARM_NEON__)
```

本仓库当前是：

```cmake
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -Wall -Wextra -DNDEBUG -O2 -ffp-contract=off -fvisibility=hidden")
```

`-ffp-contract=off` 是必需的：现有回归基线建立在"浮点累加顺序不变"的
前提上，而 `-ffp-contract=fast`（GCC/Clang 默认）会把 `a*b+c` 融成 FMA，
从而改变结果。`-O3` 实测会让设备端的 `Photo/lv` 读数从正确的
`LV90008223LVA...` 变成 `LV90008223LWA...`，所以保留 `-O2`（详见第 5 节的
修复记录）。

`-fvisibility=hidden` 已经在了，比综述的基线更好（配合
`set_source_files_properties(... COMPILE_OPTIONS "-fvisibility=default")`
只导出 JNI 需要的符号）。

### 2.3 详细路径（detailed path）不该用于生产

`processDetailed`（对应测试里的"轻量CNN"/"CRNN"方法）会：

1. 把照片缩放到长边 <= 1250 px；
2. 走完整的去影 + 透视矫正 + 切字。

实测（同一批 44 张 omtest 照片，设备端）：

| 路径 | in truth set | wall p50 | 超 200 ms |
|------|------------|----------|------------|
| `auto`（产品路径，`processFast`） | **38/41** | **56 ms** | **0** |
| `cnn`（详细路径） | 25/41 | **303 ms** | **44/44** |

**缩放把准确率从 38/41 打到 25/41。** 原因在同批照片上的对照实验：

| 缩放上限 | line2 in truth set |
|----------|-------------------|
| 1250 | **7/41** |
| 1440（不缩放） | **40/41** |
| 1600 | **40/41** |

1250 相对 1440 少了约 13% 的线性分辨率，足以把正确读法挤出 top-3 候选
集——一旦挤出，IC 约束再怎么搜都救不回来。

产品路径 `processFast` **不缩放**（在原图分辨率上定位并裁 band），所以没
受影响；`MAX_SIDE` 只作用于详细路径，且该路径的几何坐标被
`PhotoMrzPipelineTest` 断言在 1250 坐标系下，所以没有一并改掉。

**建议**：把 `MAX_SIDE` 的注释写清"这是详细路径的、有害的"，并考虑在
UI 上把详细路径标注为"仅调试/不保证耗时"，避免有人误用。或者给详细路径
也加一个"不缩放"选项。

### 2.4 缺少多帧投票与反光引导

综述建议：多帧时域投票（3-5 帧环形缓冲 + 字段级置信度加权投票）来对抗
塑封膜反光；以及直方图检测高光面积，UI 提示用户"微调角度避开反光"。

本仓库现状：

- **没有多帧投票**。`PhotoMrzPipeline.process` 是单帧的。
- **没有反光检测**。`processDetailed` 里的 "remove reflection" 只是把
  band 底部的黑边裁掉，不是高光检测。

这是**真实缺口**，而且是产品体验缺口：反光在真实拍照里很常见，单帧失败
时用户只能重拍，而 UI 不会告诉他为什么失败。

**建议优先级**（按投入产出）：

1. 先做**反光检测 + UI 引导**（成本低，收益直接）。在 fast path 的
   `fastPair` 阶段就能拿到行投影，顺便统计亮像素占比即可；超过阈值就在
   status 文字里提示。
2. 再做**多帧投票**（成本高）。但要注意综述没提的一个陷阱：多帧投票必须
   在**字段级**做，不能在整行级做——单帧的整行可能整体错，整行投票会把
   错的选出来。字段级投票的前提是有一个可靠的"这一格有多确信"的度量，
   当前只有 softmax 概率。

### 2.5 没有 ONNX / 模型可替换性

综述推荐的落地路径是"PyTorch -> ONNX -> onnx2ncnn"，好处是模型可以离线
训练、端上只跑推理。本仓库把训练和推理都放在同一个 C/Python 工具链里，
权重是生成的头文件（`cnn_weights_line1.h` / `cnn_weights_line2.h`）。

**代价**：换模型要改 C 代码 + 重新生成头文件；没有 ONNX 生态的量化、
profile、算子融合工具。

**这个代价目前是值得的**：模型只有 40 KB，一个推理框架的运行时开销
（NCNN 1.5 MB / ORT 8-12 MB）反而是大头，而且**当前准确率的瓶颈是数据
不是模型**（见下）。

## 3. 准确率的真实天花板：数据，不是模型

综述的方案 1 用 YOLOv8n-pose + CRNN，隐含假设是"通用检测器 + 通用识别器
的组合足以覆盖"。本仓库在 41 张真实照片上测到的结论相反：

- 合成基准（1380 张）上，line1 94.16% / line2 96.32% / checksum-valid
  96.09%——**合成数据上已经很好**；
- 真实照片上 40/41，剩下 1 个（`2026-9-30-AJ.jpg`）是**分类器能力边界**：
  真值要求 c28 是 'F'，网络给这一格的 'F' 概率是 0.000（它确信是 'E'），
  真值根本不在候选集里，搜索救不了；
- 真实训练切片只有 **1804 个**（line2 无歧义的仅 616 个，覆盖 36 类，
  其中 'O' **只有 1 个**）。

**所以下一步不是换更大的模型，而是加真实数据。** 两条被实测否掉的路线
（`--balance-real`、`--class-weight`，均保留在 `tools/train_cnn_omtest.py`
并标注 MEASURED AND REJECTED）都因为同一件事失败：1804 个唯一切片经不起
任何形式的重加权。

综述提到的"合成数据 + 真实数据微调"是对的，但本仓库的教训更具体：
**合成数据的字形是 12x8 位图模板放大，真实照片的字形有透视、粗细不均、
抗锯齿和截断**，两者域差距很大。要么把真实字形做成增强源（用真实切片做
模板 + 旋转/缩放/噪声生成大量样本），要么继续收真实照片。

## 4. 一个容易被忽略的风险：tie-break 噪声

设备端 38/41、宿主端 40/41，差 2 张。**这不是 bug**：宿主用 libjpeg 解码
JPEG，设备用 Skia，两者每像素差约 1 级。给宿主自己的像素加 +-1 级扰动，
就能精确复现设备的读数。翻转的恰好是那些"top-2 合法候选 log 概率相差
0.3 以内"的样本。

已实测排除的应对手段（详见 `docs/deep-beam.md`）：

- 改打分准则（只算数据位 / 加变更惩罚）：鲁棒性无改善；
- 用日期合法性做 tie-break：无改善（正确读法的日期本来就合法）；
- 把 beam 深度从 4 加到 5 或 6：输出**逐字节相同**（有上界剪枝时）。

**结论**：这是分类器区分度不够的表现，不是搜索策略的问题。**不要用搜索
侧的技巧去掩盖它**——那只会把不确定的东西藏起来。真要处理，方向是
(a) 提升分类器，或者 (b) **在结果里带上置信度**（当 top-2 合法候选的
log 概率差小于阈值时，明确告诉上层"这一格有歧义"），让业务侧决定是否
要求用户重拍。

第二点目前**没有实现**，但它是产品上最该补的：现在输出一个 44 位字符串
和一个 0-100 的 conf，调用方无法区分"确信正确"和"碰巧通过校验"。


## 5. 修复记录（本轮实施）

按上表的优先级实施了能落地且可验证的部分。

### P0-1 结果歧义标记（已实现）

C 侧 `mrz_beam_search()` 现在在找最优解的同时跟踪**次优解**；两者都在
checksum 合法集合里、且 log 概率差小于 `MRZ_AMBIGUITY_MARGIN`（0.5）时，
结果被标记为有歧义。

三个细节是必需的，否则这个标志没有判别力：

* **剪枝要留出余量**。原来的可采纳上界会把次优解直接剪掉，标志永远为
  0。把剪枝阈值放宽一个 margin 之后，次优解才到达叶子。代价是 decode
  从 1.4 ms 变成 1.4-1.7 ms，可以忽略。
* **但放宽只能在独立的第二遍搜索里做**。第一版把放宽直接加在唯一的
  搜索上，结果**最优解变了**：`Photo/lv` 从正确的
  `LV90008223LVA...` 变成 `LV90008223LWA...`。原因是打分是 log 概率的
  **累加**，而累加顺序取决于叶子被访问的顺序；放宽剪枝让更多的叶子进入
  搜索，累加顺序随之改变，近似等概率的候选之间的胜负也就翻转了。
  最终实现是**两遍搜索**：第一遍用严格剪枝找最优（与改动前逐字节一致），
  第二遍把第一遍的结果作为 incumbent、放宽剪枝，只找"比最优差的最好
  解"。第二遍永远不修改最优解。
* **第二遍的 incumbent 必须预置为最优解**，否则它记录的是自己的最优
  （也就是最优解本身），标志恒为 0；而且记录时还要跳过与 incumbent
  完全相同的字符串。
* **只算"有实质差别"的差异**（`mrz_alt_is_material`）。差异落在校验位
  列（9/19/27/42/43）、国籍列（10-12）或性别列（20）时不算风险——那些列
  要么由 checksum 决定，要么不被 checksum 保护。
* **至少差两个字符**（`MRZ_AMBIGUITY_MIN_DIFF`）。只差一个字符的次优解
  通常是某个边缘格子上的邻近类，实测它在 +-1 像素扰动下**不会**翻转；
  要求差两个字符后，去掉了 3 个假阳性而没有损失任何真阳性。

判别力（用"+-1 级像素扰动"模拟设备端与宿主端的 JPEG 解码差异）：

| | 数量 | 其中会翻转 |
|---|---|---|
| 标记为有歧义 | 18 | **4** |
| 未标记 | 23 | 1 |

4/5 的翻转被捕获，漏掉的那 1 个是 `2026-9-30-AJ.jpg`——它不是 tie-break
翻转，而是分类器把 'F' 读成了 'E'（真值概率 0.000，不在候选集内），
属于另一种失败模式，runner-up 检测原理上抓不到它。

代价是 18 个样本里有 14 个其实很稳。也就是说这个标志是**保守的**：
它会说"这行有歧义"，而实际出错的比例大约是四分之一。对"要不要请用户
重拍"这个决策来说这个方向的偏差是安全的——多提示一次重拍，比把一行错的
MRZ 当成对的写进 KYC 流程要好。

数据通路：`mrz_ocr_result_t` 新增 `line2_ambiguous` / `line2_alt_margin` /
`line2_alt`；JNI 的 JSON 新增 `ambiguous` / `altMargin` / `altLine2`；
Kotlin 的 `OcrResult` 与 `PhotoMrzResult` 透传；UI 的状态行显示
`AMBIGUOUS`，结果区显示次优读数。

### P1 反光检测与用户引导（已实现）

`MrzNative.glareFraction()` 在**与行投影同一趟像素遍历**里统计 luma >=
250（被裁剪的高光）像素的比例，不增加任何内存遍历。

阈值 `GLARE_WARN_PERMILLE = 30`（3%）。依据：MRZ 区大部分是浅色底纹，
44 张实测最高只有 6‰，所以 30‰ 是一个"干净照片绝不会触发"的水位。

UI 在检测到反光时把状态行改成"反光过曝，请微调角度重拍"。

### P2 详细路径的缩放（已修复）

`MAX_SIDE` 从 1250 提到 **1600**，与 native 热路径的
`FAST_NATIVE_MAX_WIDTH` 一致，band 因此不会被二次缩放。这把详细路径的
准确率从 25/41 拉回到 38/41（与产品路径同档），耗时从 p50 303 ms 降下来。

`PhotoMrzPipelineTest` 的几何断言改成**与缩放无关**：期望值和实测值都换算
到源图坐标再比较，因此上限以后可以自由调整而不会让测试失败。

### P2 编译选项（已调整）

Android 侧加上 `-ffp-contract=off`。

这个开关不是可选项：Clang/GCC 默认把 `a*b+c` 融成 FMA
（`-ffp-contract=fast`），那会改变浮点累加顺序，而 CNN 的回归门是
**byte-exact** 的（宿主用 `-O3 -march=native` 出权重，设备必须算出同样的
结果）。显式关掉 contraction 之后，两边的累加顺序一致。

`-O3` 本身**没有采用**：试过之后，设备上 `Photo/8` 与 `Photo/lv` 的
定位与识别结果都变了（`Photo/lv` 从正确的 `LV90008223LVA...` 变成
`LV90008223LWA...`）。宿主端同样是 `-O3` 却没变，说明差异来自
`-march=native`（宿主会启用 FMA 与更激进的向量化）与 Android 交叉
编译目标之间的组合，而不是 `-O3` 本身。风险不划算：`-O2` 已经把
native OCR 压到 40 ms，收益有限而回归风险是实的。

`-march=native` 仍然不用：库是交叉编译给 arm64-v8a 的，不能依赖构建机
的 CPU。

### 设备端最终验收（192.168.26.181，auto 产品路径）

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 44 张 omtest：line2 在真值集内 | 38/41 | **38/41** |
| 44 张 omtest：wall p50 / max | 56 / 111 ms | **62 / 75 ms** |
| 超 200 ms | 0 | **0** |
| 歧义标记 | （不存在） | 15/44 标记为有歧义 |
| 详细路径 line2 在真值集内 | 25/41 | **38/41** |

详细路径从 25/41 回到 38/41 是 `MAX_SIDE` 那个修复的直接效果；
它仍然要 310 ms（其中 172 ms 花在行定位上），所以产品路径不用它。

一个诚实的说明：**设备端还有 3 张读数与宿主端不同**（C、M、AJ），它们
**没有被歧义标记捕获**。原因是它们在设备端不是 tie-break：宿主端对 C
能找到一个几乎同分的次优读法，设备端因为 JPEG 解码器不同，切出的
字形边界略有差异，根本不存在第二个接近的合法解。歧义标记能覆盖
"两个候选难分"的情况，覆盖不了"只有一个候选但它错了"的情况——后者
要靠更多真实数据或更强的分类器。

### 回归测试

`tests/test_postproc.c` 新增 7 个断言（96 总数，全过）：

* `test_alt_diff_count` —— 两个读法的差异计数；
* `test_alt_materiality` —— 校验位/国籍/性别列上的差异不算风险，护照号

  深 beam 必须找到需要四处同时修正的合法读法，找不到时必须报告"没有解"

## 7. 不建议采纳综述里的方案

- **YOLOv8n-pose 角点检测**：现在的行投影定位在 62 张上除 3 张（`pic_scan2/2026-9-30-I,J,K`，
  MRZ 墨迹密度只有采样宽度的 5-18%，低于 `minInk` 阈值）外全部定位到两行，换成 4 顶点检测器要引入 1-2 MB 模型
  和一个失败模式（角点检错时整条链路崩掉），收益不匹配。
- **NCNN / MNN / ONNX Runtime**：40 KB 的模型用不起这些运行时（最小
  NCNN 也要 1.5 MB 库体积，ORT Mobile 8-12 MB），而且它们的核心优势
  (NEON、FP16、算子融合) 对这么小的模型收益有限——手写 NEON 更直接。
- **Tesseract 方案**：仓库里已有 Tesseract 作为兜底通道，实测它在真实
  照片上的表现明显差于 CNN（CRNN 路径 16/41 vs detailed CNN 路径 25/41，
  auto 产品路径的 CNN 引擎 38/41），且综述自己也标注"抗噪极差，不推荐商用"。
- **端侧 VLM**：> 1.5 GB / 1.5-4 s，与 200 ms 约束和设备定位都不符。
