# 2026-11-05 照片直识 OCR 深度优化（100 ms / 严禁 fallback）

## 目标
用户样本 `assets/pic/90b464ea218a9909_0001.jpg` 原耗时 848 ms、判定 FAIL、
OCR 校验未通过、Line2 尾部咬合不匹配。要求：单次 <100 ms、严禁任何 fallback、
让融合 CNN+CRNN 自己通过校验。

## 真实链路
用户截图格式来自 PC 端 `tests/gui.py::_ocr_photo_engines()`（不是 Android 端）。
baseline 848 ms 来源：Tesseract/Paddle/Indra 并发后墙钟由最慢者决定；
`mrz_arbitration.repair_line2()` 暴力枚举单次 ~250 ms（356k checksum）；
A/B/C 三个 hypothesis 各自再触发一次；临时 PPM 删除在文件 shim 下 ~58 ms。
纯 fuse 推理本身仅 15–18 ms。

## 落地改动
- `tests/gui.py`：新增 `MRZ_FAST_STRICT`（默认 1）。单次 hypothesis、只放行本机
  C 引擎（`FAST_TIER = traditional,cnn,crnn,fuse`）、默认单跑 `fuse`、
  禁 Tesseract/Indra/Paddle rescue、禁 `repair_line2`、复用固定
  `_gui_direct_fast_<tid>.ppm` 不 unlink。CS/CD 单行改用 `cnn` 而非 Tesseract。
  新增可选 `MRZ_FAST_FUSION=1`（默认关）：同批次 C 引擎逐行投票，
  用 `allow_repair=False` 跳过暴力枚举。`MRZ_FAST_TIER` 可覆盖引擎集。
  `MRZ_FAST_STRICT=0` 恢复旧路径用于 A/B。
- `tests/mrz_arbitration.py`：`arbitrate(..., allow_repair=True)` 新增开关，

## 关键结论（能力边界，勿再重复排查）
baseline 的 94 PASS **完全依赖 Tesseract/Paddle/Indra 修 line1 姓名**。
分解实验：保留旧路径全部仲裁 + A/B/C 假设重试、仅去掉三个慢引擎时，
PASS 只有 67、耗时仍 264.56 ms。TD3 line1 无校验位，四个本机 C 引擎对姓名
读的是同一批错字，投票选不出正确值（融合改了 8 处 line1、14 处 line2，
但 0 处改成 GT 正确值）。所以在「<100 ms + 严禁 fallback」硬约束下，
68 PASS 是纯 C 引擎上限，架构层面无法补回。要提 accuracy 只能重训 line1
权重或放宽禁令。

  composite@43）在 GT 上 **104~105/107 全部有效**；**line1 完全没有校验位**（位置 44 是 '<'，
  107/107 全是填充符）→ line1 只能靠分类器，不能靠算术约束。
- **权重约定（踩坑两次）**：ICAO 的 7-3-1 权重**在每个字段内重新从 7 开始**
  （C 端 `MRZ_CD_SEG1_W(c) = c-13` / `SEG2 = c-21` / `SEG3 = c-28`）。
  用行内全局权重是错的约束。Python 端必须 `weights = [WT[k%3] for k in range(len(cols))]`。
- **composite ≠ 四字段之和**：composite 把 l2[0:10]+l2[13:20]+l2[21:43] 拼成 39 字符后
  重启权重，位置 17 处权重相位与单字段不同 → composite 是**独立约束**，不是冗余。
- **DP 目标函数的教训**：单纯最大化字段联合概率会选到「同样合法但错误」的解
  （fixed=0 / broken=34）。正确策略 = **checksum 当过滤器而非目标**：
  greedy 满足该字段校验位就**保持 greedy**，只对违反的字段做 DP。修正后 broken=0。
- **最小修改数才是有效判据**：失败行普遍需要 2~4 列同时改（Photo/3-8 的 pn 字段 cols35-38
  四列全错），概率最大化在巨大的合法解空间里选不中真值；「改最少列数」先验才有效。

**68 个 line-2 错格里 40 个真值在候选集内** → 这些是**解码器可救**的，

这是「解码器缺陷」与「分类器缺陷」的分界线，比"再训训看"精确得多。

### 20.4 根因：beam 的列选择策略是错的

`mrz_ocr_cnn.c:2394-2412`：候选列按 **top-2 概率 margin 升序**排序，取前
`MRZ_BEAM_COLS`(=14) 列。**网络越自信地错，margin 越大，排得越靠后，
永远进不了候选列集合**。

实测：Photo/3 line2 的 c40 真值 `A` 是 **rank 2**，但 p_top=0.7286 / p_true=0.0001
→ margin 巨大 → 该列根本不会被搜索。

**这解释了此前所有"无效实验"**：TOPK 5→10（候选更宽，但列没被选中）、
depth 4/8/12、cols 14/24/44、WIDE_COLS 44 —— 全部恒为 36/47。
**加宽候选集对"自信的错误"无效，因为瓶颈在选列，不在候选宽度。**

### 20.5 字段级解码原型（新增 `tools/field_decode.py`）

用校验位**定位**错误字段：line2 有 5 个独立校验位
（doc 0..8/9、birth 13..18/19、expiry 21..26/27、pn 28..41/42、composite 43）。
若只有 1 个字段违规 → 错误就在该字段内 → 搜索可**限定在该字段的 ≤14 列**。

关键性质：**校验位不是被"枚举"出来的，而是由字段体"推导"出来的** ——
解码器不必在字符上压过分类器，只需在字段上压过它。

实测（topk=4, rl2_L0）：`2026-9-29-R` / `2026-9-29-T` / `2026-9-29-U` **3 个被救回**
（33 → 36 exact）。C 端现有 beam 已经做到 l2=37，所以纯 Python 原型**没有超过现状**，
但它证明了方向：**按校验位定位字段** > **按 margin 选列**。

**坑**：`tools/field_decode.py` 里手写的 ICAO 掩码是错的（line2 col0..8 应为
ALNUM+`<`，col10..12 为 ALPHA+`<`，col13..18 为 DIGIT，col20 为 M/F/<），
错掩码会产出整行垃圾（`PCIOEEDS<8AUSE...`）看起来像解码器 bug。已改为
**忠实移植 C 的 `fill_allow`**（`src/mrz_ocr_cnn.c:395-530` strict ICAO 分支）。

### 20.6 修正上一轮的错误归因：稀有类补样崩盘的真因

上一轮结论「追加式补样撑大语料量 → 训练器固定 real 总量把多数类挤掉」**不准确**。
训练器 `train_cnn_omtest.py` 用 `np.repeat(Xr, reps)[:n_real_target]` 截断：

（`IMG_*` 那批，也就是稀有 M 的来源）被系统性丢弃**。
→ 真因是**尾部截断**，不是先验被挤掉。

修正方案（`tools/aug_real_glyphs.py`）：
- 新增 `variant_plan()` / `materialize()` / `subsample_uniform()`
- 稀有类从**更宽的采样池里均匀抽样出同样数量（15）**，语料总量 60449（基线 62039，-2.6%），
  类别先验基本不变 → 不会触发截断偏差，也不会破坏先验。
- 同时**剥掉 `cand` 软标签**（软标签已实测为净负：line1 exact 39→15）。

## §21 字段级约束解码落地到C端（2026-11-06 续）

### 根因确认：beam 的列选择策略是错的

`src/mrz_ocr_cnn.c` beam 主体按 **top-2 margin 升序**选候选列（最不确定的先搜）。
**网络越自信地错，margin 越大 → 排得越靠后 → 永远进不了候选列集合。**
这解释了此前全部「无效实验」：TOPK 5→10、depth 4/8/12、cols 14/24/44、WIDE_COLS 44
全部恒为 36/47。**加宽候选集对「自信的错误」无效，瓶颈在选列不在候选宽度。**
实测 Photo/3 line2 c40 真值 `A` 是 rank 2 但 p_top=0.7286 / p_true=0.0001。

### C端字段搜索此前是「算了但没用」

字段搜索代码（`mrz_field_search` / `MRZ_FLD_BODY` / `mrz_field_cd_bad`）**一直存在**
（`src/mrz_ocr_cnn.c:2101-2217`），但算出的 `fld_best` / `fld_score` / `fld_have`
**从未被使用** —— 直接跳到 beam 搜索。这就是此前 A/B「无变化」的真正原因。

### 本轮改动（src/mrz_ocr_cnn.c）

1. **`mrz_field_solve()` 替换 `mrz_field_search()`**：beam-of-8192 + O(n²) 插入排序
   → **精确 DP**，状态 = (own, comp) 两个 mod-10 残差 = 100 状态。
   同一残差对的前缀续集完全相同 → 保留高分者**无损**，DP **精确非近似**。
   代价从「几百万次结构体拷贝」降到 (列数 × 100 × 候选数)。
2. **新增 `mrz_comp_index()` / `mrz_comp_weight()`**：composite 覆盖 39 字符
   （0..9 / 13..19 / 21..42，**含各字段自己的校验位列**），其 7/3/1 权重在
   **该39 序列上重启**，与字段内权重不同。此前漏算校验位贡献是「无解」的主因。
3. **接线**：字段搜索先在 greedy 上跑 → 产出 `fld_best`/`fld_score`（**绝对 logprob**），
   再与 beam 在**同一尺度**上竞争：beam 是 delta 空间 → 绝对分数 = greedy绝对 + delta。
   `MRZ_OCR_FIELD_SEARCH=0` 可关闭做A/B。

### 核心发现 2：**真值全部在候选集内，但整行概率低 2~80 个自然对数单位**

```text
2026-9-29-L              -2.246     -4.269    -2.023
```

### 核心发现 3：**校验位被「派生」，因此不携带任何信息**

11 个失败样本 × 4 字段 + composite：只有 2 例「读数 ≠ 派生值」

`tools/field_search_sim.py` 触发 0 次。

### 核心发现 5：**但 composite（col 43）是唯一可靠的跨字段约束**

```text
passport  n=11  pred!=gt: 0  derived==gt: 11/11
birth     n=11  pred!=gt: 0  derived==gt: 11/11
expiry    n=11  pred!=gt: 0  derived==gt: 11/11
```

### 核心发现 6：composite 约束 + top-N 前缀 DP 能让真值**可达**

`tools/topn_dp_sim.py`：DP 每残差对保留 top-K 前缀，keep=1 时真值不可达，
keep=64 时：
```text
2026-9-29-L   gt_rank=1   (top=OO1Z032II98086, gt=001Z032II98086)
2026-9-29-W   gt_rank=4
2026-9-30-AD  gt_rank=2
```

剩余 8 个样本真值不在解集（候选集里真值字符缺失或约束冲突）。

**这意味着：救回这 3 个样本需要一个「与概率无关」的判据。**

### 核心发现 7：beam 在 15/15 次改动中**总是选概率更低的行**

`tools/beam_greedy_swap.py`：beam 改动过的每一行，greedy 的整行 log-prob 都更高。
原因：beam 的 incumbent 初值是 `-1e300`，greedy 行**不是候选**，
所以 beam 接受**第一个**校验合法的叶（delta ≤ 0，必然比 greedy 差）。
